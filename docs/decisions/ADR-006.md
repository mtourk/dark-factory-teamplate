# ADR-006: GitHub Token Custody for Repo Creation (Phase 17.0)

**Status:** PROPOSED (pending Phase 17.0 implementation decision)  
**Decision Date:** 2026-10-03  
**Author:** Claude Code  
**Scope:** Phase 17.0 web intake — narrow GitHub PAT for repository creation

---

## Context

Phase 17.0 introduces the ability to create new GitHub repositories directly from the web intake interface (when a user submits a new project idea). This requires GitHub API authentication that differs from the factory's existing credential model:

- **Existing model (ADR-003):** GitHub credentials for the factory's daily operations (claiming issues, pushing code, opening PRs) live as encrypted repository secrets on **each target repository** (via GitHub Actions). The local factory process never reads them.

- **New need (Phase 17.0):** A Cloudflare Worker needs to create repositories on the user's GitHub account. This requires a **persistent credential** that the Worker can access (it runs in the cloud, not in GitHub Actions). It cannot use the same mechanism as the factory's repo-specific secrets.

---

## Decision

Store a **dedicated, narrowly-scoped GitHub Personal Access Token** as a Cloudflare Worker secret (`GITHUB_REPO_CREATE_TOKEN`). This token differs from the factory's own credentials:

- **Scope:** `repo (administration:write)`, `issues (write)`, `metadata (read)` only
- **Purpose:** Create repositories + file issues + configure labels
- **Holder:** Cloudflare Worker environment only
- **Rotation:** User-managed (via GitHub Personal Access Tokens settings)
- **Usage:** Called only by the intake Worker's `/projects` and `/conversations/:id/file-issue` endpoints

---

## Options Considered

| Option | Pros | Cons | Decision |
|--------|------|------|----------|
| **Dedicated fine-grained PAT (chosen)** | Narrow scope, explicit purpose, easy to rotate, audit trail in GitHub | Adds one more secret to manage | ✅ Selected |
| GitHub App (device flow) | More structured than PAT, better audit | Requires GitHub App setup, more complex to rotate | ❌ Deferred to Phase 17.2+ if needed |
| OAuth from browser | User-initiated, no server-side secret | Browser must handle token; ADR-005 boundary violation (cloud model interaction) | ❌ Ruled out |
| Reuse factory's credentials | Consolidate secrets | Factory creds are repo-specific (via Actions); intake is account-wide. Mixing them violates separation of concerns. | ❌ Ruled out |

---

## Rationale

1. **Narrow scope:** The token can only create repos and file issues. It cannot modify code, delete repos, or access user account settings. If compromised, blast radius is limited.

2. **Cloud-side custody (like ADR-005):** Keeps the credential **off the user's local machine** entirely. The Worker is the only consumer. This aligns with the pattern established by ADR-005 (Gemini key held by Worker, never exposed to browser or local filesystem).

3. **Clear boundary:** The token is used **only for creating repos and filing discovery issues**. All other factory operations use the existing credential model (repo secrets via GitHub Actions). This keeps concerns separate and simplifies auditing.

4. **User-managed rotation:** GitHub PAT lifetime is entirely user-controlled. No factory code needs to rotate it. If the user ever wants to revoke web repo creation, they simply revoke the token in GitHub settings.

5. **Audit trail:** GitHub logs all API calls made with this token. The user can see exactly what repos were created and what issues were filed.

---

## Consequences

**Good:**
- ✅ Web intake can create repos without user involvement in GitHub setup
- ✅ Repos auto-seeded with starter template (no manual scaffolding)
- ✅ Issues auto-filed with `factory:ready` label (ready for factory to claim)
- ✅ Clear separation from factory's own credential model

**Risk:**
- ⚠️ One more secret to manage (mitigation: GitHub PAT rotation, narrow scope)
- ⚠️ If Cloudflare Worker is compromised, this token could be exfiltrated (mitigation: narrow scope limits damage; existing factory credentials already face same risk if Actions are compromised)

**Mitigation:**
- Scope token as narrowly as GitHub allows
- Enable GitHub's token expiration (if available) for time-limited validity
- Document rotation procedure for user
- Audit logs: user can review what repos/issues were created via this token

---

## Evidence

**From ADR-005 (precedent):** Gemini API key follows the same pattern — held by Cloudflare Worker, never exposed to browser or local process. This ADR extends that principle to GitHub.

**From ADR-003 (boundary respect):** Factory's daily credentials remain GitHub Actions secrets, repo-specific. This token is new, separate, and account-wide. No existing boundary is violated.

**From Phase 17 requirement:** User explicitly wants new projects created from the web UI with minimal manual setup. This token enables that.

---

## Alternatives Deferred

**GitHub App (Phase 17.2+):** If intake scales to multiple users or organizations, a GitHub App would provide better multi-user support and more granular permissions. For now (single-user), a PAT is simpler.

**OAuth User Flow (Phase 17.2+):** If the web UI needs to support multiple GitHub accounts, browser-side OAuth could be explored. But this would require ADR-005's boundary around Gemini to expand to GitHub — not yet decided.
