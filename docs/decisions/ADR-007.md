# ADR-007: Autonomous Intake-to-Deploy Pipeline (Phase 18) — Queue, Local Build Loop, and New-App Subdomain Provisioning

**Status:** APPROVED (user decision) — design-only; implementation is a separate, explicitly approved pass
**Decision Date:** 2026-10-04
**Author:** Claude Code, with user decisions captured via `AskUserQuestion`
**Scope:** Phase 18 — what happens *after* an issue is filed via Phase 17.0 web intake, through to a deployed, reachable app

---

## Context

Phase 17.0 (web intake) files a well-formed `factory:ready` GitHub Issue, but nothing currently consumes it. The user asked for the full remaining chain, verbatim:

> "after submiting the issue, so now it should log a new issue inside my dark factory repo, and then create or edit another repo based on the selection while submitting, there should be a flag during sumission that (I have already running app) or option to create a new app in this case a subdomain on mtourk.com should be created automatically and all the flow until this app to that repo is deployed and give me back the url of it, for github and gemini secrets, it can be shared with the new repo app... ensuring that there is ability that the user can give a specific repo to edit it... so the dark factory start working once a new issue is submitted, if more than issue are submitted it should be qued, next issue is processed after the first one is done, show progress on the screen..."

Before writing this ADR, a codebase survey (read-only) established what already exists vs. what is net-new:

- **Does NOT exist today:** any running autonomous loop. `factory/cli.py`'s `submit`, `run`, `queue`, `pause`, `resume` commands all print "not yet implemented (Phase 4 backlog scheduler)" or similar. `BacklogScheduler` (`factory/backlog/scheduler.py`) and `ImplementationOrchestrator` (`factory/implementation/orchestrator.py`) are complete *library* code — selection/eligibility logic and phase-sequencing logic — but nothing calls them on a loop or a trigger. `IMPLEMENTATION_CHECKLIST.md` Phase 4's checkboxes are all unchecked.
- **Does NOT exist today:** any DNS/subdomain/Cloudflare-route automation anywhere in the repo. The only Cloudflare automation is `CloudflareAdapter` (`factory/deploy/cloudflare_adapter.py`), which deploys a Worker/Pages project but does not touch zones, routes, or custom domains.
- **Does NOT exist today:** any executing GitHub Actions workflow. `.factory/workflows/deploy.yml` is a template; `TargetRepoSetup.sync_workflow_to_target()` (`factory/deploy/target_repo_setup.py`) is a stub; secret provisioning to a target repo is `print_setup_instructions()` — it prints `gh secret set` commands for a human to run, it does not call the GitHub API.
- **Does exist, and is directly reusable:** `LocalProfileSync` (`factory/intake/local_sync.py`), an explicit stand-in that already knows how to turn a `pending_profiles` row (created by the Worker's `POST /projects`) into a local `profiles/<name>.yml` via `factory/profiles.py`'s `create_profile`/`save_profile`. It was built as a bridge *to* the loop this ADR specifies, not as the loop itself.
- **Does NOT exist today:** a queue/job table. The D1 schema (`factory/intake/worker/schema.sql`) has only `conversations`, `messages`, `pending_profiles`.

So this ADR is not "wire up the autonomous loop" — it is "design the autonomous loop," using the existing library code as its implementation substrate.

Three points were confirmed with the user via `AskUserQuestion` before this ADR was written:

1. **Where build execution runs:** the user's local machine (not GitHub Actions, not a cloud function).
2. **What a "new app" deploys as:** a Cloudflare Worker + route/custom domain, not Pages + separate DNS.
3. **What "secrets shared with the new repo app" means:** the new repo's deploys are driven by the same central credential — nothing is copied or newly minted for the new repo.
4. **Deploy credential source:** the operator's own already-authenticated `wrangler`/`gh` CLI session on the machine running the local build loop (not a dedicated token stored anywhere new).
5. **Sequencing:** write this ADR + checklist + schema design now; implement in a separate, explicitly approved pass.
6. **DNS zone:** `mtourk.com` is already on the same Cloudflare account `wrangler` is authenticated against.

---

## Decision

Add **Phase 18: Autonomous Intake-to-Deploy Pipeline**, built on five pieces:

### 1. A durable, single-flight queue (D1: `build_queue`)

Every filed issue — whether against an existing repo or a brand-new one — inserts exactly one `build_queue` row (`queued` status). The queue is the only coordination mechanism between the cloud (Worker/D1/web UI) and the local build loop; it carries no secrets, only identifiers and status text. See the schema design in `factory/intake/worker/schema_phase18.sql` for exact columns.

Rows move through: `queued → claimed → implementing → testing → reviewing → deploying → done` (or `→ failed` with an `error` column, from any state).

**One in-flight job at a time.** The local runner only claims a new row once the previous one reaches `done`/`failed`. Claiming is a conditional `UPDATE build_queue SET status='claimed' WHERE id=? AND status='queued'` — even if two runner instances were accidentally started, only one can win a given row, so the single-flight guarantee holds at the database level, not just by convention.

### 2. A local build loop (new: `factory/intake/queue_runner.py`)

This is the piece that makes "the Dark Factory start working once an issue is submitted" literally true. It is a long-running process the user starts on their own machine (the existing local-execution model, per ADR-001/ADR-005 and the user's own confirmation above) that:

1. Polls `GET /build-queue?status=queued` on an interval.
2. Claims the oldest queued row via `POST /build-queue/:id/claim`.
3. Resolves/creates the local profile via the existing `LocalProfileSync` (bridges `pending_profiles`/the new repo's info into `profiles/<name>.yml` through `factory/profiles.py`) — this is the first real caller `LocalProfileSync` has ever had.
4. Drives the existing `ImplementationOrchestrator` (`factory/implementation/orchestrator.py`) through its phases (`ImplementationPhase` — already modeled, just never invoked by anything autonomous) and `BacklogScheduler` for eligibility/priority if more than one issue is ever queued on the same profile.
5. After each phase transition, calls `POST /build-queue/:id/progress` with a short step name + detail string, so the cloud side (and the web UI polling it) always reflects current reality without the local loop needing any inbound network exposure.
6. On success for a `needs_new_app` job, runs the deploy step (next section) and reports the final URL. On failure at any step, reports `failed` with the error and leaves the profile/branch intact for manual inspection — it does not retry automatically (matches Phase 14's existing "escalate, don't silently retry" posture).

This is this ADR's answer to Phase 4: the backlog scheduler finally gets an execution context, scoped specifically to issues arriving through Phase 17's intake channels.

**Operational consequence, stated plainly so it isn't a surprise later:** autonomous processing only happens while this process is running on the user's machine. There is no cloud-hosted equivalent — that was the explicit, confirmed choice.

### 3. New-app deploy: Worker + Custom Domain, using the operator's own ambient CLI session

When a job's target is a brand-new app (`needs_new_app = true`), the queue runner, after implementation/tests pass:

1. Runs `wrangler deploy` for the new repo's Worker, using whatever Cloudflare authentication is already active in the local `wrangler` session on that machine (the same session the user has used manually, by hand, throughout this project's deployment history to date).
2. Attaches a Cloudflare **Custom Domain** — not a bare Route — at `<project-slug>.mtourk.com`, via the Cloudflare DNS API (programmatic, fully automated). The provisioning is specified in detail in `docs/operations/CLOUDFLARE_DNS_AUTOMATION.md` — this includes exact API endpoints, error handling, retry logic, and Python implementation hints. **One hostname maps to exactly one resource** (learned from a real Phase 17.0 incident — see that doc's "Critical Rule" section): before this step, the runner determines whether the new app is Worker-only, Pages+Worker, or Pages-only, and the custom domain `<project-slug>.mtourk.com` goes to whichever resource serves the user-facing frontend (Pages, if one exists; the Worker only if there is no separate frontend). If the app has both a Pages frontend and a Worker API, the Worker either keeps its ambient `*.workers.dev` domain or gets a second, distinct hostname (`api-<project-slug>.mtourk.com`) — never the same hostname as Pages.
3. Reports the final `https://<project-slug>.mtourk.com` URL back via the progress endpoint, which becomes the `done` state's payload the web UI links to.

**No new secret is created, stored, or transmitted by the deploy step itself.** The `wrangler` session is already authenticated locally. DNS provisioning uses a Cloudflare API token held in a Worker secret (following the same pattern as ADR-005/006), fetched by the runner at startup. This is a deliberate, narrow exception to ADR-003's "Cloudflare credentials live only in GitHub Actions repo secrets" default — justified the same way ADR-005 and ADR-006 justify their own narrow exceptions: it is scoped to exactly one operation (new-app DNS provisioning), it introduces zero new credential-custody surface (nothing is minted or copied; the operator's pre-existing CLI session is simply used, the same way it already has been for every Worker deploy performed by hand in this project so far), and editing an *existing* repo never uses this path — that continues to go through the existing repo's own GitHub Actions secrets per ADR-003/ADR-004, unchanged.

### 4. Shared capability, not shared secrets, for the new app

Per the user's confirmed answer, the new app's own Worker does **not** receive a copy of `GEMINI_API_KEY` or `GITHUB_REPO_CREATE_TOKEN`. If the new app's feature needs either capability, it is wired at build time to call the existing central Intake Worker's endpoints (which already hold those secrets) rather than being handed its own copy. This keeps the secret count constant as the number of spawned apps grows — the attack surface is the one central Worker, not N per-app copies.

### 5. Visibility: a tracking issue on the Dark Factory repo itself

Satisfying "it should log a new issue inside my dark factory repo" literally, without making `dark-factory-teamplate` a build target (which would reopen ADR-002/004's deliberately-closed question of the factory managing itself): filing an issue through Phase 17.0 now also files a lightweight **tracking issue** on `dark-factory-teamplate`, cross-linked by URL with the real issue on the target repo. It carries no acceptance criteria and is never claimed by any build loop — it is a visibility/audit record only, closed automatically when the corresponding `build_queue` row reaches `done`/`failed`.

### 6. Editing an existing repo

The repo-selection modal (already built in Phase 17.0, pending deploy) gains one more control: a checkbox, "Also deploy after this change" — default off for existing repos. If left off, the queue runner implements and opens a PR exactly as the current factory design intends (human merge gate preserved). If checked, the deploy step runs against that repo's *existing* Worker (its `profiles/<name>.yml` already records which one, from however that repo was originally onboarded) rather than provisioning a new subdomain.

### 7. Mid-flight issue amendments (new, ADR-007 §7)

While a job is processing (any status between `claimed` and `deploying`), the web UI exposes an **"Add Detail"** panel that lets the user append context to the issue without interrupting the current job:

1. User types or pastes additional context (clarifications, forgotten acceptance criteria, constraints, etc.) into the UI.
2. A `POST /build-queue/:id/append-detail` endpoint (new, Worker-side) receives the text, appends it as a comment to the GitHub issue, and records it in a new `build_queue_updates` table (see schema below) for audit/visibility.
3. The local queue runner, at the start of each phase transition, reads the latest GitHub issue body + comments to pick up any user-submitted amendments. This way additions naturally flow into the current/next phase's evaluation — if amendments change what a BMAD critic would conclude, the critic sees them on the next loop.
4. No amendments trigger a restart or priority bump — they are purely additive and flow through the normal phase progression. If an amendment is significant enough to warrant re-analysis, the runner is already running the same critics it would need to re-run; they just see fresher input.

This keeps the UI responsive (user never waits for a phase to finish, they can add details immediately) and the queue logic simple (amendments are just comments, no special handling).

### 8. Progress UI

The web app's success screen is replaced by a **status screen** that polls `GET /build-queue/:id` every few seconds and renders: current step, a done/remaining step list, and — once `done` — the live URL (new app) or PR link (existing-repo edit). This is the direct answer to "show progress on the screen and information in which step the factory is now, what is done and what is left."

## Options Considered

1. **GitHub Actions drives the new-app deploy** (consistent with ADR-003/004's existing per-repo-secret model) — rejected per the user's explicit answer; would require minting and copying a Cloudflare credential to every newly created repo, which is exactly the "secrets shared with the new app" outcome the user asked to avoid.
2. **A dedicated Cloudflare API token held centrally (Worker secret), fetched by the local runner at deploy time** — considered and offered to the user as the alternative to option 3; not chosen, because it introduces a new secret-fetch-to-local-machine exception for no benefit over the option actually chosen.
3. **The operator's own ambient `wrangler`/`gh` CLI session on the local build-loop machine** (chosen) — zero new custody surface, matches how every Worker deploy in this project has already been performed by hand all session.
4. **Pages + manual DNS CNAME per new app** — rejected per the user's explicit "Cloudflare Worker + route" answer; also would require a separate DNS automation step the Custom Domain feature avoids.
5. **Factory manages itself for this feature** (i.e., `dark-factory-teamplate`'s own issues drive this build) — rejected; the tracking-issue approach (§5 above) gets the visibility the user asked for without reopening ADR-002/004.

---

## Rationale

- Every new piece of automation here is the smallest extension of something that already exists: the queue reuses D1 the same way `conversations`/`pending_profiles` already do; the runner is a caller for library code (`BacklogScheduler`, `ImplementationOrchestrator`, `LocalProfileSync`) that was built but never invoked; the deploy step reuses a credential the user already manages by hand, rather than inventing a new one; the tracking issue reuses the existing GitHub Issue mechanism rather than a new audit log.
- The single new precedent — using an ambient local CLI session as a deploy credential instead of a GitHub Actions secret — is scoped as tightly as ADR-005/006's precedents were, and only applies to the one path (new-app provisioning) where the user explicitly chose it over the alternative.

## Consequences

- `factory/intake/worker/schema_phase18.sql` (new, proposed migration — **not yet applied to the live D1 database**) adds `build_queue`.
- New Worker routes (not yet implemented): `GET /build-queue`, `POST /build-queue/:id/claim`, `POST /build-queue/:id/progress`, `GET /build-queue/:id`.
- New local module (not yet implemented): `factory/intake/queue_runner.py`.
- `factory/cli.py`'s `run`/`queue`/`pause`/`resume` stubs become real once this phase lands — this is the first phase that actually resolves those "not yet implemented (Phase 4...)" placeholders.
- `IMPLEMENTATION_CHECKLIST.md` gains a Phase 18 section (added alongside this ADR).
- Web intake (`index.html`/`app.js`) needs the "already running app?" flag at submission time, the existing-repo "also deploy" checkbox, and the progress-polling status screen — all implementation, deferred to the approved build pass.
- Operationally, the user must keep `queue_runner.py` running on their machine for autonomous processing to happen at all; this is a direct, confirmed consequence of choosing local execution over a cloud-hosted loop.
